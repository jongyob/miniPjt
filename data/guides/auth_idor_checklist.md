# 인증/인가 및 IDOR 체크리스트

> 이 문서는 `npm audit`/`eslint`/PMD/SpotBugs 같은 정적 분석 도구가 **패턴 매칭만으로는
> 원천적으로 판단할 수 없는** 인증/인가·비즈니스 로직 취약점을 정리한 사내 가이드입니다.
> 이런 취약점은 지금까지 모의해킹(사람이 직접 시나리오를 짜서 코드 흐름을 이해해야 찾는
> 방식)에서만 드러났습니다. `security_agent`는 이 문서를 근거로 코드를 리뷰합니다.

## 1. IDOR / 깨진 객체 수준 권한 부여 (OWASP API1:2023 Broken Object Level Authorization)

리소스 ID(주문 ID, 사용자 ID, 파일 ID 등)를 파라미터로 받는 조회·수정·삭제 API는 반드시
**"요청을 보낸 사용자가 그 리소스의 소유자이거나 접근 권한이 있는지"**를 서버 쪽에서
검증해야 합니다. ID 값 자체가 유효한지(존재하는지)만 확인하고 소유권을 확인하지 않으면,
다른 사용자의 ID를 순차적으로 대입해 접근할 수 있습니다(IDOR).

- **위반 예시**: `getOrder(orderId)`가 `orderId`로 주문을 그대로 조회해 반환하고,
  호출자의 `currentUserId`와 그 주문의 소유자를 비교하는 코드가 없음.
- **올바른 패턴**: 조회한 리소스의 소유자 필드(`user_id` 등)와 현재 인증된 사용자를
  비교해, 일치하지 않으면 403(Forbidden)을 반환.
- **정적 도구가 못 잡는 이유**: 코드 문법만 보면 정상적인 DB 조회문이라 패턴 매칭 대상이
  없습니다. "이 조회 결과가 누구 것인지"와 "지금 누가 요청했는지"를 비교하는 논리가
  **없다는 사실**을 알아채려면 비즈니스 맥락을 이해해야 합니다.

## 2. 함수 수준 권한 부여 누락 (OWASP API5:2023 Broken Function Level Authorization)

관리자 전용 기능(사용자 삭제, 권한 변경, 전체 데이터 내보내기 등)에 역할(role) 검증이
빠져 있으면, 일반 사용자도 URL이나 함수를 직접 호출해 관리자 기능을 실행할 수 있습니다.

- **체크 포인트**: 엔드포인트/컨트롤러 메서드 이름에 "admin", "delete", "export" 등이
  있는데 역할 확인 코드가 없는 경우.

## 3. 인증 우회 조건

디버그 플래그, 특정 헤더 존재 여부, 테스트 계정 하드코딩 등으로 정상적인 인증·세션 검증을
건너뛰는 분기가 남아 있는지 확인합니다. 개발 편의를 위해 넣었다가 프로덕션 코드에 그대로
남는 경우가 흔합니다.

## 4. 대량 할당 (Mass Assignment)

클라이언트가 보낸 요청 객체를 통째로 엔티티에 매핑해 저장하면, 서버만 관리해야 할 필드
(`role`, `isAdmin`, `price`, `balance` 등)까지 클라이언트가 덮어쓸 수 있습니다.

- **체크 포인트**: 요청 DTO와 저장 엔티티가 1:1로 매핑되는지, 민감 필드가 화이트리스트
  방식으로 걸러지는지 확인합니다.

## 5. 비즈니스 워크플로우 우회

여러 단계로 이뤄진 흐름(장바구니 → 결제 → 주문 확정)에서, 중간 단계를 검증하지 않고
최종 API를 직접 호출하면 상태를 건너뛸 수 있는지 확인합니다(예: 결제 완료 여부 확인 없이
주문 확정 처리).

## 6. 레이스 컨디션 (TOCTOU)

잔액 확인 → 차감, 재고 확인 → 차감처럼 "확인"과 "반영" 사이에 시간 간격이 있는 로직은
동시 요청 시 검증을 우회당할 수 있습니다(Time-Of-Check to Time-Of-Use). 확인과 반영을
하나의 원자적 연산(DB 트랜잭션 + 락, 또는 조건부 UPDATE)으로 묶었는지 확인합니다.
