# 부하 유발 위험 패턴 체크리스트

> 이 문서는 코드만 봐서는 "패턴상 의심된다" 이상을 말하기 어렵고, 실제 부하테스트(k6/
> JMeter/Locust 등)를 돌려봐야 확정되는 성능 위험 패턴을 정리한 사내 가이드입니다.
> `performance_agent`는 이 문서를 근거로, 정적 도구가 놓치기 쉬운 "부하 상황에서만
> 드러나는" 병목 후보를 코드에서 찾아 설명합니다.

## 1. N+1 쿼리

목록을 한 번 조회한 뒤, 그 목록의 각 항목마다 반복문 안에서 별도 쿼리를 또 던지는
패턴입니다. 목록 크기가 커지거나 동시 요청이 늘면 DB에 날아가는 쿼리 수가 "항목 수 ×
동시 요청 수"로 선형 폭증합니다.

- **위반 예시**: 주문 목록을 조회한 뒤, 각 주문의 상품명을 얻으려고 주문마다
  `SELECT product_name FROM order_items WHERE order_id = ?`를 반복 실행.
- **올바른 패턴**: `IN` 절이나 JOIN으로 한 번에 조회(배치 조회), 또는 필요한 필드를
  처음 쿼리에 포함.
- **정적 도구가 못 잡는 이유**: 반복문 안에 쿼리 호출이 있다는 것 자체는 문법적으로
  정상 코드라, "이게 항목 수만큼 반복돼서 위험하다"는 판단은 제어 흐름(반복문 범위,
  반복 횟수의 크기)을 이해해야 합니다. 일반적인 무료 정적분석 도구에 이를 안정적으로
  잡는 내장 규칙이 마땅치 않습니다.

## 2. 페이지네이션 부재

목록 조회 API가 `LIMIT`/`OFFSET`(또는 커서 기반 페이징) 없이 테이블 전체를 반환하면,
데이터가 쌓일수록 응답 시간과 메모리 사용량이 함께 늘어납니다. 특히 동시 사용자가 많을
때 DB·애플리케이션 서버 메모리를 동시에 압박합니다.

- **체크 포인트**: `findAll()`류 메서드를 그대로 API 응답에 쓰는지, 클라이언트가 페이지
  파라미터를 보내는데 서버가 이를 무시하고 항상 전체를 반환하는지 확인합니다.

## 3. 동기 블로킹 I/O

요청을 처리하는 스레드 안에서 외부 API 호출·파일 I/O·긴 계산을 타임아웃 없이 동기적으로
수행하면, 외부 서비스가 느려지는 순간 요청 처리 스레드가 그대로 묶여 스레드 풀이
고갈됩니다(연쇄 장애).

- **체크 포인트**: 외부 HTTP 호출에 타임아웃이 설정돼 있는지, 재시도 로직이 무한정
  반복되지 않는지 확인합니다.

## 4. 캐시 부재

자주 조회되지만 자주 바뀌지 않는 데이터(공통 코드, 설정값, 카테고리 목록 등)를 매
요청마다 DB에서 새로 조회하면, 실제로는 캐시 한 번이면 되는 조회가 트래픽에 비례해
DB 부하로 직결됩니다.

## 5. 커넥션 풀 미설정/과소 설정

DB 커넥션 풀 크기가 예상 동시 사용자 수 대비 지나치게 작거나(또는 풀 설정 자체가 없어
매 요청마다 새 커넥션을 생성), 부하가 몰리면 커넥션 획득 대기가 응답 지연의 주 원인이
됩니다.

- **체크 포인트**: 커넥션 풀 크기 설정이 코드/설정 파일에 있는지, 트래픽 예상치와 맞는
  값인지 확인합니다(전체설계 3-5절 "DB 연결과 부하 파라미터 입력"이 이 판단을 구체화하는
  로드맵 항목입니다).

## 6. 무거운 연산의 동기 실행

리포트 생성, 이미지·파일 처리 같은 무거운 작업을 비동기 큐(메시지 큐, 백그라운드 작업)
없이 요청 스레드에서 즉시 처리하면, 해당 요청이 몰리는 시간대에 다른 요청까지 함께
느려집니다.
