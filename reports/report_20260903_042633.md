### PERF-1 [high] OrderService.java:20 (그룹 G-8)

- 도구: `llm-review` / 규칙: `n-plus-one-query`
- 요약: 반복문 안에서 order_items 테이블을 order_id 컬럼으로 조회하는 N+1 쿼리 패턴이 감지됨. orderIds 리스트의 각 항목마다 별도의 쿼리가 실행되어 성능 저하를 초래합니다.
- 상세: 반복문 안에서 order_items 테이블을 order_id 컬럼으로 조회하는 N+1 쿼리 패턴이 감지됨. orderIds 리스트의 각 항목마다 별도의 쿼리가 실행되어 성능 저하를 초래합니다. [DB 실행계획: SCAN order_items — 풀스캔 확인(인덱스 없음). 예상 부하: 동시 사용자 200명, 분당 요청 3000건] [실제 부하테스트: GET /orders/1/items에 동시 요청 50건(부하 프로파일 예상 동시 사용자 200명 기준, 로컬 서버 보호를 위해 50건으로 상한)을 보낸 결과 p95 지연시간 962ms, 에러율 0%가 관측되었습니다. 임계치(300ms) 초과로 동시 부하 상황에서 실제로 지연이 발생함을 실측으로 확인했습니다.]
- 근거 문서: `load_risk_checklist` — 목록을 한 번 조회한 뒤, 그 목록의 각 항목마다 반복문 안에서 별도 쿼리를 또 던지는
패턴입니다. 목록 크기가 커지거나 동시 요청이 늘면 DB에 날아가는 쿼리 수가 "항목 수 ×
동시 요청 수"로 선형 폭증합니다.  
- **위반 예시**: 주문 목록을 조회한 뒤, 각 주문의 상품명을 얻으려고 주문마다
`SELECT product_name FROM order_items WHERE order_id = ?`를 반복 실행.
- **올바른 패턴**: `IN` 절이나 JOIN으로 한 번에 조회(배치 조회), 또는 필요한 필드를
처음 쿼리에 포함.
- **정적 도구가 못 잡는 이유**: 반복문 안에 쿼리 호출이 있다는 것 자체는 문법적으로
정상 코드라, "이게 항목 수만큼 반복돼서 위험하다"는 판단은 제어 흐름(반복문 범위,
반복 횟수의 크기)을 이해해야 합니다. 일반적인 무료 정적분석 도구에 이를 안정적으로
잡는 내장 규칙이 마땅치 않습니다.
